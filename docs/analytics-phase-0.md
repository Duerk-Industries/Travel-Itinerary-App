### Load baseline

Cloud Monitoring `run.googleapis.com/request_count`, filtered to the production service and summed across revisions into UTC hourly buckets, returned **251,465 requests** in the 30-day interval **2026-09-08 16:11 UTC to 2026-10-08 16:11 UTC**. The busiest UTC hour ended around **2026-09-21 20:00 UTC** with **4,061 requests**. The Phase 0 decision's 10× peak is **40,610 requests/hour** (about 11.3 requests/second), before adding proposed analytics traffic. The monitored count includes all request types and is not a count of engaged users. Tests should use realistic burst/concurrency patterns and add modeled analytics batches; average requests/second alone is insufficient.

At the implementation plan's example of 1,000 consenting monthly users × 8 sessions × 25 events, estimate 200,000 events/month and about 10,000 20-event client batches. With the initial one-document-per-event Firestore design, those are about 200,000 event writes before rollups, retries, deletes and indexes. Recalculate with actual consent uptake, event size, regional Firestore prices and invoice data. [Firestore billing reference](https://firebase.google.com/docs/firestore/pricing).

## Initial event and metric dictionary

The following is the Phase 0 product schema decision. Phase 2 will create the typed runtime registry and validate values server-side. All behavioral rows require a current `product_analytics` grant; approved detailed diagnostics use a separate permission. Per-user/tier denominators exclude users without consent for the period, and dashboards display that exclusion.

| Event | Trigger and success meaning | Minimal properties | Eligible population |
|---|---|---|---|
| `session_started` | Signed-in app becomes foreground after 30 minutes idle; one per session | platform, app version | Consenting account users |
| `engaged_session_summary` | Session closes or reaches a bounded checkpoint; foreground time only | duration bucket, platform | Consenting account users |
| `feature_viewed` | Named feature becomes visibly usable, once per feature/session/trip | feature, entry point enum | Users with feature access then |
| `trip_reference_viewed` | Itinerary/reservation/overview reference visibly rendered | feature, trip ref, phase | Consenting account travelers with trip access |
| `task_started` | Explicit start of wizard, edit, import, invitation or other named task | task enum, attempt ID | Users able to start that task |
| `task_cancelled` / `task_failed` | Explicit cancellation or terminal failure, with the attempt ID | task enum, coarse failure code | Started attempts |
| `trip_created` | Server commit of trip creation; one operation ID | trip ref, operation ID | Consenting creators |
| `item_saved` | Server commit of transfer/lodging/activity/car/expense/packing item | item type, operation ID, trip ref | Consenting authorized members |
| `invite_accepted` | Server confirms group/trip invitation acceptance | invite type, operation ID | Consenting invited accounts |
| `generation_requested` | User explicitly requests AI generation | generation ID, trip ref | Eligible consenting users |
| `itinerary_viewed` / `itinerary_edited` | Result rendered / edit committed | generation or itinerary ref, trip ref | Consenting travelers with access |
| `import_completed` | Server confirms usable import result | import type, outcome, item-count bucket | Consenting initiators; restricted-source review required |
| `map_link_opened` | User opens a map link from a trip reference | map provider enum, trip ref | Consenting trip users |
| `report_exported` | Cost report export initiated and completed | report type, result | Consenting authorized users |
| `packing_item_checked` | Confirmed packing state change | trip ref, checked state | Consenting authorized users |

The trusted cost ledger is a separate operational schema: provider attempt ID, initiating user, optional trip, feature, provider/model, units, price version, estimated microdollars, billable outcome, cache state, adjustment and reconciliation state. Its lawful purpose and retention require review before deployment. Client events never set their own subject, tier, consent epoch or authorized trip.

**Metric definitions:** feature reach = consenting unique viewers / consenting active eligible users; meaningful adoption = consenting unique users with completed action or engaged read / same eligible population; task completion = terminal successes / mature started attempts; repeat use = returners / mature first-use cohort; direct cost = sum of settled priced units with unknown amounts reported separately; technical success and p50/p95 are by feature/platform/version; platform mix has web, iOS, Android and both-platform account cohorts; during-trip engagement counts traveler-trip pairs with meaningful activity during scheduled trip-local dates / eligible consenting traveler-trip pairs. Report median and p95 per-user cost, consent coverage, event delivery coverage, metric version and excluded/unknown populations alongside the rate.

Trip phase uses inclusive trip-local dates. Decision 5's fallback is segment timezone, trip timezone, then event device timezone, else unknown; save which level was used and keep date/timezone revision. A device timezone is an unverified proxy, so show fallback coverage. A 10-second visible reference is the proposed engaged-read threshold; task abandonment is 30 minutes without progress for interactive forms, while async jobs close on their server terminal outcome. Validate both thresholds in a canary before relying on them for product decisions. Do not backfill pre-consent behavior.

Allowlisted dimensions: feature enum, task enum, outcome/failure enum, platform, coarse browser/OS family, app version, role/tier, trip phase, source, consent epoch and UTC date. Do not put user IDs, trip IDs, provider request IDs or raw URLs in metric labels. Pseudonymous subject/trip references remain restricted personal data in the event store. Exclude message text, prompts, booking references, precise location, destination text, financial transactions and Google/Plaid content-derived fields.

### DPIA screening and legitimate-interest review

Screening result: **complete a DPIA before optional collection**. The proposed program follows individual feature paths over time, joins records to trip dates and costs, and can reveal travel patterns and group relationships even without GPS. Group content can identify companions who never consented to analytics. Pseudonyms are reversible in the service. These features create enough potential impact to require a documented full assessment before deciding risk is low; no automated consequential decision or advertising profile is intended. Use opt-in, property allowlists, access separation, retention and small-cohort suppression as planned mitigations. Examine residual risk, third-party processors and non-account companions in the DPIA. A DPIA is a living assessment completed before high-risk processing starts. [European Commission DPIA guidance](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/obligations_en).

Preliminary legitimate-interests assessment for necessary security logs and limited cost controls: (1) purpose: operate, secure, rate-limit and financially administer the service; (2) necessity: HTTP status/duration, protected request IDs, limited quota units and priced attempts support these purposes, while full URLs, prompt content or long user-linked history are harder to justify; (3) balancing: short retention, restricted access, redacted fields, export/rights routes and no behavioral reuse reduce but do not remove the privacy impact. The privacy owner must approve a purpose-by-purpose assessment and consider whether contract or legal obligation is the better basis for particular records. Optional feature tracking is outside this assessment and remains opt-in. [ICO legitimate-interests assessment](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/lawful-basis/legitimate-interests/).
