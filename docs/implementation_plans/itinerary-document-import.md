# Itinerary Document Import — Implementation Plan

**Status:** Implemented.
**Last updated:** 2026-08-18
**Authors:** assistant, in collaboration with @bryanduerk
**Related:** [itinerary-narrative-depth-and-validation.md](itinerary-narrative-depth-and-validation.md) (the reverse
direction of this feature — generating a rich narrative document *from* structured trip data; this plan reads
one back *into* structured trip data). `server/src/ingestion/` (email/booking-confirmation ingestion — see §1 for
why this is a new, adjacent service rather than an extension of that pipeline).

---

## 1. Summary

A user who already has a finished, hand-written or externally-produced itinerary document (the two examples this
plan was scoped against — a 28-day Japan itinerary and a 15-day Romania road trip, both rich markdown/PDF
documents with day-by-day schedules, a lodging table, a hikes table, and a practical-notes section) should be able
to hand it to the app and have it populate their trip: flights/transfers, lodging stays, activities, and car
rentals added to the appropriate tabs, and everything else that doesn't map to a bookable item — luggage
logistics, entry requirements, safety notes, booking-priority ordering, foliage/seasonal timing — captured as
free text rather than silently discarded.

Three decisions fixed for this plan (superseding the open questions raised when this was first sketched):

1. **Every imported item lands with `status: 'Proposed'`.** Not a `needsBooking`-driven split between `'Needed'`
   and `'Booked'` — a document the app has never seen before should never assert something is booked on the
   user's behalf. `'Proposed'` is the correct point in the existing lifecycle
   (`Needed → Proposed → Booked → Completed | Cancelled`, `server/src/utils/itineraryStatus.ts`): the user
   already decided on this itinerary (unlike a `'Needed'` gap the app is asking them to fill), but nothing here
   has been confirmed as an actual reservation.
2. **A new free-text `notes` field on `Trip`**, surfaced on the Overview page, holds everything the extraction
   pass found genuinely useful but couldn't turn into a structured item — practical notes, warnings, logistics.
   Appended to, never overwritten, across multiple imports.
3. **Gated to Premium tier**, following the existing ingestion precedent (`docs/tiers.md`: *"Free users must not
   see the manual upload entry point or access ingestion endpoints. Premium and Pro users can access the ingest
   tab..."*) — same shape of capability, same tier boundary.

### 1.1 Naming collision to resolve first

This session already added a collapsible **"Trip Notes"** section to the Overview page (P0 of
[itinerary-narrative-depth-and-validation.md](itinerary-narrative-depth-and-validation.md)) showing the
AI-generated `itinerary.planMarkdown` — read-only, regenerated by the AI itinerary pipeline. The field this plan
adds is different in every respect: user-editable, sourced from document import (and hand-typed edits after
that), and lives on `Trip`, not `Itinerary`. Shipping both under the label "Trip Notes" would be confusing in the
UI and in code review. **Rename the existing AI section's heading to "Trip Guide"** (variable/testID names in
`overview.tsx` — `itineraryPlanMarkdown`, `showItineraryPlanNotes`, `renderItineraryPlanNotes`,
`overview-plan-notes-card` etc. — are already accurately named around "plan," not "notes," so no rename needed
there) and give this plan's new field the heading **"Notes"**, matching the literal request. Do this rename in
the same change that adds the new field, not as a follow-up, so there's never a commit where both sections read
"Trip Notes."

## 3. Data model changes

### 3.1 `Trip.notes`

```ts
// server/src/types.ts
export interface Trip {
  // ...unchanged fields
  notes?: string | null;
}
```

Postgres migration (idempotent, alongside the existing pattern in `db.postgres.ts`'s `initDb()`):

```sql
ALTER TABLE trips ADD COLUMN IF NOT EXISTS notes TEXT;
```

`db.postgres.ts` and `db.firebase.ts`: `createTrip`/`updateTrip`/`getTripById`/`listTrips`-family functions gain
`notes` alongside `description` — same nullable-string handling, no new validation.

### 3.2 `PATCH /api/trips/:id`

`server/src/routes/tripRoutes.ts`'s existing handler (`:793`) destructures `description` and a fixed field list,
rejects the request if every field is `null`. Add `notes` to both the destructure and the "at least one field"
guard, matching `description`'s exact handling (`typeof notes === 'string' ? notes : null`).

### 3.3 Client

`app/tabs/overview.tsx`: mirror `descriptionDraft`/`resetDrafts()`/`saveOverviewEdits()` exactly —
`notesDraft` state, included in the edit-mode payload, a `TextInput` alongside the description field. Manual
edits and imported content share one field and one save path; there is no separate "imported notes" vs.
"my notes" — see §4.3 for why appends carry their own visual separator instead of a second field.

## 4. Pipeline design

### 4.1 Stage 1 — Extract candidates from document text

```ts
// server/src/services/itineraryDocumentImportService.ts

export type ItineraryImportCandidateType =
  | 'flight' | 'rail' | 'ferry_bus_transfer' | 'hotel' | 'car_rental' | 'tour_activity';
// Deliberately a subset of ingestion's ParsedItemType — no restaurant_reservation/event_ticket/
// generic_note. "Dinner in Lipscani" or "check the tide table" is day-detail color, not a new
// trip-item section; pulling every dinner mention into the Activities tab would flood it with
// noise nobody asked to import. Only things that map to a real trip tab.

export type ItineraryImportCandidate = {
  type: ItineraryImportCandidateType;
  name: string;                          // "Poarta Schei 18, Brașov" / "BOS → NRT" / "Zărnești Gorge"
  date: string | null;                   // ISO YYYY-MM-DD — departure/check-in/pickup/activity date
  endDate: string | null;                // check-out/dropoff date; null for single-day items
  location: string | null;
  notes: string | null;                  // duration, elevation gain, booking caveats — carried per item
  sourceExcerpt: string;                 // verbatim source line(s), for the confirmation UI
  flight?: { departureLocation: string | null; arrivalLocation: string | null; carrier: string | null };
  hotel?: { address: string | null };
  carRental?: { pickupLocation: string | null; dropoffLocation: string | null; vendor: string | null };
  activity?: { activityType: string | null; startLocation: string | null };
};

export const extractItineraryDocumentCandidates = async (params: {
  documentText: string;
  userId: string;
  tripStartDate?: string | null;         // narrows year inference for dates like "Nov 23" with no year
  tripEndDate?: string | null;
}): Promise<{
  candidates: ItineraryImportCandidate[];
  unassignedNotes: string;               // §4.3
  usage: { promptTokens: number; completionTokens: number; estimatedCostUsd: number };
}>
```

- **Primary pass plus bounded activity recovery.** The primary whole-document call preserves cross-day context
  for transfers, lodging, rentals, and trip-wide notes. A deterministic day-section parser then sends bounded
  groups of dated days through a dedicated activity pass so large activity tables cannot exhaust the primary
  response budget. Every detected day must produce an activity or day note. Input is capped at 60k characters,
  which covers the reviewed Romania and Japan PDFs without silently truncating them.
- **Prompt asks for the mixed array directly**, not `llmExtractor.ts`'s single-`itemType` shape. System prompt
  enumerates all six candidate types with the fields above. Same "never invent a date, name, or address that
  isn't in the text" discipline as `p3_validate.md` elsewhere in this codebase — a wrong import that silently
  pollutes a real trip is worse than one that skips an ambiguous line.
- No `status`/`needsBooking` field to extract anymore (§1, decision 1) — one fewer thing for the model to get
  wrong.
- Gated the same way as `llmExtractor.ts`: `getActiveAiProvider` / `getConfiguredProviderApiKey` /
  `reserveApiUsageOrThrow`, new feature key `itinerary_document_import` (§6) checked *before* this stage runs,
  not after spending the tokens.

### 4.2 Stage 2 — Dedup against the trip's actual records

```ts
export type ItineraryImportMatch = {
  candidateIndex: number;
  existingId: string;
  existingType: ItineraryImportCandidateType;
  reason: string;
};

export const findExistingTripItemMatches = (
  candidates: ItineraryImportCandidate[],
  existing: { flights: Flight[]; lodgings: Lodging[]; activities: Activity[]; carRentals: CarRental[] }
): ItineraryImportMatch[]
```

Per-type match rules — loose on purpose, since the same trip item is rarely worded identically twice:

| Candidate type | Matches an existing record when |
|---|---|
| flight / rail / ferry | same trip, `departureDate` within ±1 day, **and** normalized departure-or-arrival location overlaps (handles "Narita" vs "NRT" vs "Keisei-Narita") |
| hotel | date ranges overlap **and** (normalized name shares a token, e.g. "Poarta Schei" ⊂ "Poarta Schei 18, Brașov") **or** normalized address overlaps |
| tour_activity | same date **and** normalized name is a substring either direction — the exact technique `entryByName`/`mergeCuratedWithDiscovered` already use in `attractionsCatalogService.ts` |
| car_rental | `pickupDate` matches **and** normalized vendor or pickup location overlaps |

Pure function, no DB/AI calls, unit-testable in isolation — the same shape as `findParsedItemByFingerprint` but
scoped to a trip's live records instead of ingestion history, which is the actual gap being closed (§2).

### 4.3 Stage 3 — Notes text (the non-assigned information)

The extraction prompt (§4.1) also returns `unassignedNotes`: everything in the document that's useful
trip-planning information but doesn't correspond to a specific bookable item — practical tips, entry
requirements, packing/luggage logistics, weather/seasonal notes, safety warnings, currency/payment notes, the
booking-priority ordering, foliage/timing tables. The model is told to render it as clean markdown, preserving
concrete specifics (numbers, thresholds, names) and dropping anything that duplicates what's already captured as
a structured candidate — the Romania document's "Passes... A 7-day nationwide JR Pass..." wait, its luggage
paragraph and bear-safety paragraph are exactly this; its per-day activity lines are not.

This text does **not** carry the same "never invent" guardrail as structured candidates in the same way —
it's landing in a free-text field presented for the user's own review and editing, not asserted as validated
structured data. It should still not fabricate specifics absent from the source, but a slightly-off summary
sentence here is a UX quality issue, not a data-integrity one the way a wrong flight date would be.

**Append, never overwrite.** Structured items get an "already part of the trip" check (§4.2); notes get the
equivalent courtesy — new imported text is appended to any existing `Trip.notes` under a labeled section, so a
second import (or the user's own hand-typed notes) is never silently clobbered:

```
### Imported from japan-only-schedule.md — 2026-08-18

<unassignedNotes content>
```

### 4.4 Stage 4 — Write

```ts
export type ItineraryDocumentImportResult = {
  added: Array<{ type: ItineraryImportCandidateType; id: string; name: string }>;
  skippedDuplicates: Array<{ type: ItineraryImportCandidateType; name: string; matchedExistingId: string; reason: string }>;
  skippedUnparseable: Array<{ excerpt: string; reason: string }>;
  notesAppended: boolean;
  usage: { promptTokens: number; completionTokens: number; estimatedCostUsd: number };
};

export const importItineraryDocumentIntoTrip = async (params: {
  userId: string;
  tripId: string;
  documentText: string;
  sourceFilename?: string | null;        // for the notes-section label, §4.3
  dryRun?: boolean;                      // preview without writing — mirrors IngestionPayload.dryRun
}): Promise<ItineraryDocumentImportResult>
```

For each non-duplicate candidate, map into the `Omit<Flight,'id'|'sharedWith'>` / `Omit<Activity,'id'|'createdAt'>`
/ etc. shape, set `status: 'Proposed'` unconditionally, and call the matching `insert*` function. Append
`unassignedNotes` to `Trip.notes` via the same `updateTrip` path as §3.2, guarded by "only if non-empty" —
an import that found nothing loose shouldn't leave a stray empty section header.

`dryRun: true` runs stages 1–3 and returns what *would* happen (including the notes text that would be
appended) without writing anything — the first UI surface: show the user a diff before touching their trip,
then a second call with `dryRun: false` on confirmation.

## 5. Route and UI

- **New route**, not folded into `ingestionRoutes.ts` — this bypasses the review queue by design. A user pasting
  their own finished itinerary has already decided these are real; batch-confirming forty rows one at a time in
  the existing review UI would be the wrong UX for this input shape. `POST /api/trips/:tripId/import-document`,
  entitlement-gated (§6), accepts either raw text or an uploaded file (routed through `normalizeIngestionPayload`
  first for PDFs, same as manual-upload ingestion intake).
- **UI entry point**: a new action on the trip Overview page — "Import from document" — text area or file
  picker, calls with `dryRun: true` first, shows the added/skipped/notes-preview breakdown, user confirms,
  second call with `dryRun: false`. Hidden entirely for Free tier, same as the existing manual-upload entry point
  (`docs/tiers.md`: *"Free users must not see the manual upload entry point"*) — confirm against whatever
  client-side tier check currently hides that button (the `ingestion.tsx` tier-visibility logic from the earlier
  "Limit who sees ingest" work this session referenced) and reuse it rather than writing a second check.
- **Notes field**: new "Notes" section on Overview, editable via the existing edit-mode pattern (§3.3), placed
  near the (now-renamed, §1.1) "Trip Guide" section so the two are visually distinct in the same scroll region.

## 6. Tier gating

New feature key `itinerary_document_import`, seeded the same way `cost_tracking`/`flight_parser` already are in
`entitlementService.ts`'s `seedEntitlementDefaults`:

```ts
['free', 'itinerary_document_import', false],
['premium', 'itinerary_document_import', true],
['pro', 'itinerary_document_import', true],
```

Checked via `assertCanUseFeature(userId, 'itinerary_document_import', role)` at the top of the route handler,
before Stage 1 spends any tokens — same ordering as `overview_weather`'s `assertCanUseFeature` call in
`itineraryRoutes.ts`. Feature flags have no admin bypass (per CLAUDE.md); tier entitlements do, consistent with
every other capability in this table.

The new `Trip.notes` field itself is **not** tier-gated — a Free-tier user who received a shared trip with notes
already on it (imported by a Premium collaborator) can still read and edit them. Only the import action that
*populates* notes via extraction is gated.

## 8. Rollout

1. Land the `Trip.notes` migration + `PATCH` support + Overview UI field first (§3), independent of the import
   feature — it's useful on its own and de-risks the larger change.
2. Land the "Trip Notes" → "Trip Guide" rename (§1.1) in the same change, so there's no window where both
   sections share a label.
3. Land Stage 2 (`findExistingTripItemMatches`) next — no AI dependency, the clearest test surface, and the piece
   every other stage depends on for correctness.
4. Land Stage 1 + Stage 4 together behind the `itinerary_document_import` feature flag, defaulted off, gated to
   Premium tier per §6, before wiring the UI entry point.
5. UI entry point last, once an admin has manually exercised the route end-to-end against both example documents.

## 9. Explicitly out of scope

- Editing extracted candidates before confirmation (accept/reject only, no inline field editing in the dry-run
  preview) — a reasonable v2, not required to ship v1 usefully.
- Re-import / update-in-place for an item that was previously imported and has since been edited by the user —
  first pass only adds; it never modifies or removes an existing record, even one it previously created.
- Native (non-web) file upload for this flow — scope to web first, matching where manual-upload ingestion started.

## 10. Addendum (2026-08-19): converted to an async job

**Problem:** `POST /api/trips/:tripId/import-document` was implemented as a single synchronous request —
upload/paste → normalize (OCR or PDF text extraction) → LLM extraction → DB writes, all in one HTTP
round-trip. In production this returned `HTTP 502` to users. Root cause: `firebase.json` rewrites `/api/**` to
Cloud Run, and Firebase Hosting enforces a **fixed ~60s timeout on that rewrite that cannot be raised**,
independent of Cloud Run's own `timeoutSeconds` (300s here). A real document import was observed taking 121s
end-to-end — Hosting killed the connection with its own 502 well before Cloud Run's response arrived, even
though the import was still running successfully server-side.

**Fix:** mirrors the existing async-job pattern already used for AI itinerary generation
(`itineraryAsyncService.ts` / `POST+GET /api/itinerary/async/:jobId`):

- `documentImportAsyncService.ts` — new in-memory job queue (`queued → running → completed | failed`),
  independent from the itinerary-generation job map. `enqueueAsyncDocumentImportJob` schedules the work via
  `setTimeout(0)` and returns immediately; the job itself runs `normalizeIngestionPayload` (only when the
  request was a file upload — pasted text needs no normalization) followed by `importItineraryDocument`.
- `POST /api/trips/:tripId/import-document` now does only the fast, validating work inline — entitlement
  check, multer upload + virus scan — then enqueues and responds `202 { jobId, status: 'queued' }`. Any
  synchronous validation failure (bad tier, bad file type, virus scan fail) still fails immediately with its
  original status code; nothing about that error path changed.
- `GET /api/trips/:tripId/import-document/:jobId` — new polling endpoint, scoped to `job.userId` and
  `job.tripId` matching the request (404 otherwise). Returns `{ status, error, result }`, same shape
  `importItineraryDocument` used to return directly.
- `ItineraryDocumentImport.tsx` now polls this endpoint every 3s (5 min timeout) after submit, instead of
  awaiting a single `fetch`. UX is unchanged from the user's perspective — same "Analyzing document…" busy
  state — it just no longer times out on slow documents.

Test coverage: `server/__tests__/document-import-async.test.ts` — 202-then-poll happy path, failure surfaced
as a failed job rather than a hung/thrown request, tier-gating still fails fast pre-enqueue, and job
ownership is enforced on the GET endpoint (404 for another user's job id).

## 11. Addendum (2026-10-21): WanderBunnies printouts import completely

**Problem:** importing an itinerary that WanderBunnies itself printed (Overview → Print itinerary → PDF)
brought in only the first flight. The model-driven pipeline was a poor fit for that layout: the extracted
text glues each label to its value (`Departure12:00 · BOSArrival16:10 · NRT`), a booking is printed on every
day it appears (a flight on its departure and arrival days, a hotel on each night), a 30-day trip is far past
one response's output budget, and the duplicate matcher treated any two transfers on adjacent days that
shared one endpoint (for example, both arriving at Tokyo) as the same trip.

**Fix:**

- `server/src/services/wanderBunniesPrintParser.ts` reads the app's own printout deterministically. It is
  selected by `isWanderBunniesPrint` (the "TRAVEL ITINERARY" title, the "Printed from WanderBunnies" footer and
  `DAY n` headings), and `extractItineraryDocumentCandidates` uses it before any AI call: no provider key, no
  cost, same result on every run. Other documents still use the model pipeline unchanged.
- Recovered: flights, trains, buses, ferries and private/other transfers (route, times, carrier, number,
  booking reference, travelers, layover, cost), lodging (stay dates, address, rooms, status, refund-by, total,
  per night), activities (date, time, location, duration, status, reference, cost, free-cancellation date),
  car rentals (vendor, vehicle, pick-up/drop-off date and place, reference, prepaid, cost, note), and day-plan
  places, notes and checklists with their time, cost and entries. Status is kept as printed.
- A booking printed on several days becomes one record: transfers repeated on consecutive days (up to two for
  flights) merge, with the last day as the arrival date, and lodging and rentals are keyed by name and dates.
  Items keep the dates printed in the document, not the target trip's dates.
- Duplicate matching is tighter for everything: transfers sharing one endpoint are duplicates only when their
  departure times agree or are unknown, and two activities with the same name on a day are one only when their
  start times agree or are unknown (a morning and an evening visit are two).
- The 60,000-character limit exists for the model, so printouts get a 400,000-character bound.

Known limits: the printout carries no activity category (imported as "Other"), no currency per item (amounts
are taken in the trip's currency), no coordinates, and no per-person split. Note bodies are not printed, so
imported notes carry only their title. Identical entries listed twice on one day are treated as one.

Tests: `server/__tests__/wanderBunniesPrintImport.test.ts` covers the parser on a printout fixture in the
extracted-text format, the full import (inserts, preview, re-import adds nothing, no AI provider used) and
the two matcher changes.

## 12. Addendum (2026-10-21): category, coordinates and currency in the printout

Follow-up to §11, closing three of its "known limits".

**Export** (`app/utils/printableItinerary.ts`):

- Activities print a `Category` field (their activity type).
- Lodging, activities and car rentals print `Coordinates` (`41.40363, 2.17436`) and a `Coordinate source`
  (`catalog`, `airport`, `manual` or `geocoder`) only when the item has valid coordinates. Car rentals print
  `Pick-up coordinates` and `Drop-off coordinates`. Out-of-range values are never printed. Flights print none:
  their airports are known from the IATA code.
- A car rental's note is now a labeled `Notes` field instead of a loose paragraph, so it can be read back
  unambiguously. Older printouts, where the note followed the cost, still import.
- Currency was already printed on the cover and in every cost (`USD 752.97`); nothing item-level changes, because
  items store no currency of their own.

**Import** (`wanderBunniesPrintParser.ts`, `itineraryDocumentImportService.ts`):

- `Category` becomes the activity type when it is one of the app's types, otherwise the activity is "Other".
- Coordinates are restored with their recorded source; an unrecognized source is treated as `manual`, and
  impossible values are ignored. Printouts made before this change have none and import as before.
- Storage is the new adapter function `setItemCoordinates(userId, kind, itemId, coordinates)` (lodging, activity
  or car rental), implemented for Postgres (also used by the in-memory test adapter) and Firestore and exposed
  through `db.ts`. It checks the caller belongs to the item's trip, and returns false for an item that does not
  exist. The existing insert functions are unchanged. The Postgres ones never wrote coordinate columns, and the
  same is true of the other planning writes, which update them separately.
- A failed coordinate save never fails the import: the item is added without a pin and the result carries a
  warning.
- The cover currency is compared with the trip's currency. If they differ, the result carries a warning and the
  Imports preview shows "Check: ..." above the items. Amounts are imported as printed, not converted, because
  there is no per-item currency or rate to convert with. Printouts and trips in the same currency show nothing.
- The print parser now also accepts text where the extractor puts a space between each label and its value
  (`FLIGHT BOS → NRT`, `Departure 12:00 · BOS`), and ignores a repeat of the trip title that a browser's print
  header can add between pages.

Still not carried by a printout: flight coordinates, per-person cost splits, and the body of a note.

Tests: `server/__tests__/item-coordinates.test.ts` (real adapter, run on both the in-memory adapter and the
Firestore emulator), `server/__tests__/wanderBunniesPrintImport.test.ts` (category, coordinates, labeled notes,
currency warning, failed coordinate save, spaced text) and `app/tests/printableItinerary.test.ts`.
